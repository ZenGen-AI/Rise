# 设计文档写作规范

本目录是 RismForge 的系统设计文档集。读者有两类:人类架构师,以及只能靠文档独立理解系统的 AI。本文规定所有文档的结构、写法和图例,写作者必须照此执行。

## 2. 自包含,是硬规则

1. 不写指向其他文档、计划、补充章节的跳转,例如"见 X 节"、"详见计划 5"。需要的上下文就地写出,宁可重复。
2. 每篇文档都含"系统速览"共享区块。它由工具维护,只改 `_shared/` 里的源文件。
3. 提到别的子系统,用它的名字,并在"接口契约"一章写清:本文依赖它什么,它依赖本文什么。
4. 决策编号可以出现,但同一处必须写出决策内容。不能只丢一个编号。
5. 引用代码时,路径和符号必须真实存在,检查脚本会核对。尚未落地的接口标 [计划中],签名来自实施计划,实施时可能微调。
6. 不叙述写作过程。不写"评审发现"、"我选择"、"已修复"。每条设计写成现在时的事实,加理由,加判错的代价。

## 3. 状态标记

- **[已落地]**:代码在主干上且有测试。
- **[计划中]**:设计与实施计划已定,代码还没写。
- **[推迟]**:明确不在 V1 范围内。

模块表、接口表、产物表都带状态列。头部写明基线提交,读者据此判断文档与代码的距离。

## 4. 子系统文档的统一结构

章节编号和标题固定,没有内容的章写"无"并说明原因。

| 章 | 要回答的问题 | 必含内容 |
|---|---|---|
| 头部 | 这篇讲什么,现在到哪一步 | 元信息表:状态、所在层、代码位置、基线提交、依赖、被依赖、对应实施计划 |
| 0 系统速览 | 整个系统是什么样 | 共享区块,原样 |
| 1 定位 | 它是什么,解决什么问题,在系统里站哪 | 一句话定义,上下文图,与邻居的关系 |
| 2 目标、非目标与约束 | 做什么,不做什么,受什么限制 | 目标清单,非目标清单(含推迟项),质量属性与硬约束 |
| 3 架构 | 由哪些部分组成,怎么协作 | 组件图,模块表(模块、职责、依赖、状态),依赖方向规则 |
| 4 数据模型与状态机 | 管什么数据,状态怎么走 | 实体表,产物与路径表,状态机图,不变量 |
| 5 接口契约 | 别人怎么用它,它用别人什么 | 入口签名(契约级),产物读写约定,触发条件,对邻居的假设 |
| 6 关键流程 | 典型场景下谁在何时做什么 | 主流程图,失败与恢复路径,一个带具体数值的走查例子 |
| 7 关键决策 | 为什么这么设计 | 决策表:编号、决策、备选、理由、判错的代价 |
| 8 失败处理与可观测 | 出错怎么办,怎么看 | T1、T2、T3 分类表,留痕产物,只读观测手段 |
| 9 测试策略 | 怎么证明它是对的 | 分层测试表,替身清单,不依赖的外部服务 |
| 10 现状、局限与未核实项 | 做了什么,没做什么,没核实什么 | 已落地与计划中清单,已知局限,未核实项(含核实办法),明确不做 |
| 附 本文术语 | 本文独有的词 | 术语表 |

头部元信息表的行固定为:一句话、状态、所在层、代码位置、基线提交、依赖、被依赖、对应实施计划。骨架见 `TEMPLATE.md`。「对应实施计划」只写工作包编号与任务范围,不写文件路径。

决策编号:闭环集成阶段已有的 R1 到 R21 保留原编号。其余用"缩写-序号",缩写为 SYS、CP、SS、DX、MT、AC、MA、RS、SE、TS、TP、BR、FC,依次对应系统总体、ControlPlane、SocialSimulator、诊断评测、MindTrainer、Actio、MindAgent、RecipeStore、策略经验、TrainScheduler、TrainPlanner、外部推理桥接、factory。

总览文档的结构不同,见其自身目录,但同样遵守本文第 2、3、5、6 节。

## 5. 写法

- 先结论后细节。每节第一句给出结论。
- 表格优于长段落。一张表不超过 7 列。
- 一句话不超过 40 个汉字,一个段落不超过 5 句。
- 数字放进表里,不写在叙述句里。
- 代码块只放契约级签名,不超过 15 行,不放实现。
- 中文叙述,英文标识符原样保留,首次出现时给中文解释。
- 不用"可能"、"大概"、"应该"。拿不准的事写进第 10 章的未核实项,并写明怎么核实。
- 一个概念只有一个名字,全套文档统一。

## 6. 图

- 只用 SVG,由 `diagrams/svgkit.py` 生成。不用位图,不用 ASCII 框图,不用 Mermaid。
- 一张图回答一个问题,一般不超过 12 个节点(总体架构图可到 16),一个主方向,尽量不交叉。检查脚本对超过 12 个节点告警,超过 16 个报错。
- 颜色语义固定:蓝是控制层,绿是计算层,紫是共享基础设施,橙是人工门与人工动作,青是存储,灰是中性与外部,红是失败与风险。
- 图只画目标系统,不标进展。图里不出现「计划中」「已落地」「推迟」「V1 现状」一类字样,也不用虚线或灰框表示没做完。进展写在正文的状态标记、状态列与「现状」章。
- 虚线只表达设计事实,如人工直接改文件、只存引用、下一 tick 重入、别的写方、禁止的导入。图里用了虚线,图例必须写明含义。
- 制图库出图时扫描全部可见文字、标题与说明,出现进展字样直接报错。
- 图的种类限五种:上下文图、组件图、流程图(带编号的步骤)、状态机图、数据流图。
- 每张图都带文字版(节点与连线),由工具自动生成并嵌在图下。图里不能有文字版没有的信息。
- 工作流:在 `diagrams/` 里写 `fig_<名字>.py`(暴露 `build()`,返回画布),运行 `build_all.py` 生成 SVG,在文档里放同名占位标记,再运行同步脚本。
- 目检:每张图提交前必须渲染成位图看一遍。逐项确认文字没有被截断,连线没有穿过无关方框,标签没有遮住箭头,图例与正文一致。

## 7. 维护

- 改共享内容只改 `_shared/*.md`,然后运行同步脚本。
- 改图只改 `diagrams/` 里的脚本,然后重新生成并同步。
- 提交前运行检查脚本。

## 8. 并行写作的约定

- 每位写作者只改自己负责的 `NN-名字.md` 和以自己文档编号开头的图(`fig_NN-*.py`)。
- 不改 `svgkit.py`、`tools/`、`STYLE.md`、`TEMPLATE.md`、`_shared/`。需要绘图库的新能力,在自己的 `fig_*.py` 里绕过,并在交付报告里说明。
- 不执行任何写入型 git 命令,由总负责人统一提交。
- 事实来源的优先级:已落地部分以代码为准;计划中部分以闭环集成设计与施工计划为准;更早的设计文档只作背景,与前两者冲突时一律作废。
- 引用的每个文件路径、函数名、常量、数值都要对着代码或计划核实,不凭记忆写。

## 9. 写作流程与交付

按顺序做,每一步都有产出。

1. **读规范与全局。** 读 `STYLE.md`、`TEMPLATE.md`、`00-overview.md` 全文。总览定下的名字、状态标记、依赖方向和术语,你的文档必须沿用,不得另起。
2. **读来源。** 先读代码与测试,再读施工计划与闭环集成设计,最后才读旧设计。施工计划很长,不要通读:读头部、全局约束、文件表、任务标题和你要用的对外契约小节,其余用 grep 定位。
3. **列大纲。** 按 `TEMPLATE.md` 的章节,每章列出要写的表和图。图定 3 到 5 张:上下文图、组件图、关键流程图,有状态机时加状态机图。
4. **先画图。** 写 `diagrams/fig_<文档编号>-<主题>-<类型>.py`,例如 `fig_10-controlplane-architecture.py`,生成的图就叫 `10-controlplane-architecture`。用法与常见坑见 `diagrams/README.md`。
5. **再写文。** 图下写 3 到 5 句读图说明,正文以表为主,图用 figure 占位标记引用。
6. **同步与检查。** 带文档名运行 `sync_docs.py` 与 `check_docs.py`。错误必须为 0。符号告警逐条处理:改正名字,或在该行补 [计划中]。其余告警给出理由,或消除。
7. **目检。** 每张图渲染成 PNG,用 Read 打开逐张看。确认文字没有截断,连线没有穿过无关方框,标签没有遮住箭头,图例与正文一致。不合格就改图重来。
8. **交付回报。** 见本节末。

### 核实规则

- 已落地部分的每个路径、符号、常量、默认值、数量都以代码为准。数量用命令得出:用例数用 `uv run pytest --collect-only -q <文件>`,行数用 `wc -l`,常量用 grep。
- 走查例子的数值必须能在代码或测试里对上。需要实跑时,用 `uv run python -c` 在仓库里跑,不改仓库文件。临时文件放 `/Users/jaredguo-mini/.claude/jobs/3ca32a58/tmp`,不放 `/tmp`。
- 旧设计没有写明理由的决策,不要编造理由。理由列写"原设计未记录理由,代码表现为……",判错的代价写你能从代码或测试推出的后果。
- 代码与施工计划不一致、计划与计划不一致、旧设计与代码不一致,都在回报里逐条列出。正文按"代码 > 施工计划 > 闭环集成设计 > 旧设计"的优先级写。
- 不跑全量测试。只收集或只跑与你相关的测试文件。

### 统一口径

| 概念 | 统一写法 | 不要写 |
|---|---|---|
| 协调层 | ControlPlane | 控制平面、协调器 |
| 产物树 | 产物树,即 git 仓库里的 `control-plane/` 目录 | 状态库、数据库 |
| 产物通用格式 | 信封 | 包装、元数据头 |
| 驱动循环 | 调和循环 | 事件循环、调度循环 |
| 下发指令的可注入函数 | 派发器(Dispatcher) | 执行器(留给训练执行器) |
| 注入调和循环的动作函数 | 处理器(Handler) | 回调、钩子 |

「回调」与「钩子」的限制只针对注入调和循环的动作函数。仿真层与服务层的 `on_turn`、`on_session_closed` 是代码里的正式名字,文档沿用原名。
| 人工审核点 | 审核门①、②、③ | 审批、闸门 |
| 绕过 ControlPlane 的实时调用 | 受限直连,接口①、接口② | 旁路、特例通道 |
| 训练产出 | 候选 checkpoint | 候选模型 |
| 下一轮训练的起点 | 基座,即最新 effective 的 zengen 版本 | 底座。底座只指开源基础模型 |
| 九个施工单元 | 工作包 N | 计划 N、Plan N |
| 诊断报告可信度 | 证据等级 `stub`、`mock`、`real` | 真实度 |
| 失败类别 | T1 瞬态、T2 确定性、T3 需人工 | |
| 版本 | V1、V2 | v1、v2 |

### 常见错误

- 把计划中的接口写成已落地。判断依据只有一个:代码里有没有。
- 旧设计与代码不一致时照抄旧设计。
- 叙述写作过程:"评审发现"、"后来修复"、"我选择"。
- 同一概念前后用两个名字。
- 表格超过 7 列,或一格里塞整段话。
- 在叙述句里堆数字。数字放表里。
- 图里有文字版没有的信息,或图与正文的名字不一致。
- 一张图塞满。超过 12 个节点就拆。

### 交付回报

不超过 250 字,包含四项,不复述文档内容:

1. 文档与图的路径、行数、`check_docs.py` 的结果。
2. 发现的矛盾:代码与计划之间、计划与计划之间、旧设计与代码之间、你的文档与 `00-overview.md` 之间。逐条写出处。
3. 你不确定、需要总负责人裁决的事。
4. 你没有核实的事实,以及原因。
