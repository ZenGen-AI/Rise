# Starling 记忆服务：rise 一侧的需求

日期 2026-11-02。读者：在 Starling 仓库里做改造的开发者。本文只说 rise 需要什么、为什么要，以及 rise 现在怎么用 Starling；Starling 内部怎么实现，由 Starling 一侧决定。

## 1. 为什么要改

rise（RismForge）现在在自己的进程里直接 `starling.Memory.open(db_path)`，每个人格一个 `.db`，散落在本机的记忆根目录下。代码在 `src/actio/memory_starling.py`（全仓库只有这一个文件导入 `starling`）。

这样有两个问题：

1. **隔离靠 rise 拼文件**。Starling 自己有世界的概念，世界里有主体（holder），可以把多个主体的记忆放在一起、各自隔离。rise 没有用上，靠一人一个文件来隔离。
2. **在 Starling 里看不到、管不了**。这些库不在 Starling 的世界注册表里，Starling 的看板和管理界面看不到 rise 里任何 agent 的记忆。用户要能在 Starling 里查看、管理所有 agent 的记忆，**包括训练时每个会话的临时副本**。会话还在跑时要能实时看，会话结束后要留着复盘。

## 2. 目标

- Starling 作为一个服务进程运行。rise 用 **Starling 提供的 Python 客户端**连它，不再自己打开库文件。
- rise 的配置里给了 Starling 服务地址，就连这个地址。没给，rise 按钉住的 Starling 版本在本机自己拉起一个服务，只监听回环地址。拉起和停止由 rise 负责，Starling 要做的是让这件事好做（第 6 节）。
- rise 里所有记忆都进 Starling 的世界，在看板里能看到，包括部署记忆、训练副本和验证用的临时副本。

## 3. 非目标

- **这一步不换机器**。服务和 rise（以及 rise 里的 Simulator）在同一台开发机上。以后会一起搬到 GPU 主机，但不在这一步。所以这一步只用回环地址，不要求公网鉴权、TLS 或跨机传文件。
- **不改记忆语义**。抽取、嵌入、召回、摘要算法都照旧。rise 要的是现有门面能力的服务化，不是新的记忆功能。
- **不换抽取和嵌入端点**。服务照旧调 OpenAI 兼容端点，由 rise 传配置（第 5.6 节）。

## 4. rise 现在怎么用 Starling

Starling 侧做服务和客户端时，要保证下面这些用法都还能实现。

### 4.1 门面调用（`starling.Memory`）

| rise 的用法 | 调用 | 备注 |
|---|---|---|
| 打开一个人格的库 | `Memory.open(path, agent=persona_id, llm=..., embedder=...)` | 抽取和嵌入用 `make_openai_llm` 与 `make_openai_embedder` 造，带 `timeout_ms`、`max_retries`，rise 设 `max_retries=0` |
| 召回 | `recall(query, k=limit, mode="semantic", strict=True, include_volatile=True)` | 用到命中的 `content_id`、`score`、`row` 的 `subject_id`、`predicate`、`object_value`、`polarity`、`modality`、`confidence` |
| 幂等写入 | `remember_event(key, text, interlocutor=..., epoch="2026-01-01T00:00:00Z")` | 用到 `statement_ids`、`extraction_failed`、`failure_category`；同 key 同文本重入返回同一批语句、不二次抽取 |
| 语句 id 换内容 id | `content_ids(statement_ids)` | 本库没有的 id 映射成 `"missing"` |
| 补嵌入 | `embed_pending(now)`，`now` 由 rise 按事件时钟给（`EPOCH + next_seq()` 秒） | 用到 `next_seq()`，以及 `embedded`、`failed` 两个计数 |
| 放弃事件 | `abandon_event(key)` | 已提交抛 `EventConflict`，未知 key 抛 `KeyError` |
| 待处理事件 | `pending_events()` | 用到每项的 `key` |
| 逻辑摘要 | `digest()` | 进训练配置的 `config_hash`，见 4.3 |
| 备份 | `backup_to(path)` | 用于部署轮次的起点副本和验证快照。服务化以后由 5.4 的快照代替，客户端不提供这个方法 |
| 关闭 | `close(timeout=...)` | 超时说明还有在途调用，rise 据此决定删不删副本 |
| 版本与提示词 | `starling.__version__`、`starling.ExtractionConfig()` 的默认值 | 进记忆运行时身份 |

rise 识别的异常：`RecallDegradedError`（瞬态）、`EventConflict`、`MemoryClosed`，其余一律当永久失败。

### 4.2 rise 里有哪些库，各自什么生命周期

| 库 | 现在的位置 | 谁在写 | 生命周期 |
|---|---|---|---|
| 部署记忆 | `deploy/<persona_id>.db` | MindAgent 部署会话；门②（`admit`）收录 | 长期。每次部署 episode 前 `backup_to` 一份起点副本，失败时 `restore_from` 覆盖回去 |
| 部署起点副本 | `snapshots/<round_id>/<episode_id>-<persona_id>.db` | 不写 | 轮次收尾时删掉，或用来回滚 |
| 验证快照与临时库 | `snapshots/<round_id>/verify-<persona_id>.db`，临时库在 `verify-scratch/` 下 | 只读重放 | 轮次内用完就删 |
| 训练种子 | `seeds/<seed_id>/<persona_id>.db` | 人放进去，rise 只读 | 长期 |
| 训练副本（对手位） | `runs/<run_id>/<session_id>/<slot_id>.db` | 一个会话里的一个对手位 | 从种子复制而来，会话终态即删 |
| 训练副本（训练位） | `runs/<run_id>/client/<episode_id>/<slot_id>.db` | 一条 rollout 的训练位 | 从种子复制而来，rollout 终态即删 |

**关于并发**：rise 今天的 rollout 是顺序跑的（`src/mindtrainer/trajectory_source.py:250`）。但同一时刻仍有好几份库开着：部署记忆、当前会话里每个对手位一份、训练位一份；部署轮次和训练也可能交错。**同一组 rollout 都从同一个起点出发，彼此看不到对方写的东西。**

### 4.3 摘要的用途（硬约束）

- 训练开始前，rise 对每个人格算起点摘要，连同记忆运行时身份一起写进训练配置、进 `config_hash`。续训时任何一项变了，判为不同实验。
- 同一组 rollout 的起点摘要必须相同。副本的摘要必须等于种子的摘要。
- 部署回滚后，rise 核对恢复后的摘要等于备份时的摘要。

所以：**分叉或复制出来的副本，摘要必须等于来源**；**快照恢复后，摘要必须等于快照时**。摘要和打开时的 agent 名无关（今天就是如此）。

### 4.4 进程、并发与规模（实测）

- **一个控制面仓库同一时刻只有一个 rise 进程在写。** `run` 和 `reconcile` 启动时会取仓库的排他文件锁，第二个进程拿不到锁，直接退出（`docs/design/90-factory-and-cli.md` 的 FC-14）。记忆根目录第一次使用时登记在一个仓库名下，其他仓库用不了（`claim_memory_root`）。所以 rise 自己拉起的服务只会有一个 rise 客户端；用户给的外部服务可能有几个仓库共用。
- **这个 rise 进程里有多个线程。** 实时服务端的会话处理、轨迹源、部署轮次各占线程。同一份部署记忆会被端口和管理面调用同时用到。同一人格上的写，今天靠 rise 的人格锁串行化。
- **规模。** 现在只有一份真实部署库，920 KB，是场景三验证时留下的，还没有任何种子。一个训练步要开的副本数是 `groups_per_step × group_size ×（1 个训练位 + 对手位数）`。rollout 顺序跑，所以同一时刻开着的只是一组会话的那几份。
- **GIL。** rise 的集成测试发现，Starling `20de8a1` 的 `SemanticRetriever.vector_recall` 绑定在等查询嵌入的 HTTP 响应时不释放 GIL，同进程的其他 Python 线程全被卡住（见 `tests/starling_fakes.py` 的模块文档）。服务端一个进程同时开多个世界时，一个世界的召回会因此卡住所有世界。

## 5. 需求

编号用于在 Starling 一侧对照。**必须**是 rise 接上去的前提，**最好**是有了更顺手。

### 5.1 一个服务同时开多个世界（必须）

- 一个服务进程能同时打开多个世界并接受读写，按世界名路由。现在的看板只有一个活动世界，切换就是换引擎（世界设计 §8.1），满足不了 4.2 那几份库同时在用。
- 世界的数量：同一时刻**打开着**的只有十几个以内，即部署记忆加上一组会话的训练副本，外加看板临时点开的几个。为复盘保留下来的副本受 5.7 的上限约束，注册表里会有几百到上千个世界。
- 不再用的世界可以关掉（不删），复盘时再按需打开，或者只读打开。
- **一个世界在等网络时，不能挡住其他世界**（见 4.4 的 GIL 一条）。抽取、嵌入的 HTTP 等待期间要释放 GIL，否则就得把世界隔离到不同的进程里。
- **句柄模型**（rise 一侧的默认，Starling 可以改）：
  - 句柄属于一个客户端会话。同一个会话可以多次打开同一个世界，这些句柄共用一个引擎。
  - 另一个会话再打开同一个世界时，拒绝写入，并返回可以区分的错误码。rise 会给世界名加上本仓库的前缀，所以共用外部服务的几个仓库不会撞名。
  - 客户端断开或租约过期时，它的句柄全部释放。5.4 的"还有打开的连接就拒绝恢复"只数活着的句柄。

### 5.2 世界与主体怎么对应（必须，具体形状由 Starling 定）

rise 的建议是：

- **部署记忆是一个世界**，每个人格是其中一个主体（holder）。
- **训练副本各自是独立的世界**。"一个世界文件至多一个租户"（世界设计 §6）加上同组 rollout 互不可见，所以副本不能挤在同一个世界里。
- 种子也是世界，或者是世界的快照。

如果 Starling 认为另一种对应更合适（比如每个人格一个世界），也可以，但 5.3 到 5.5 要能按 rise 的粒度做到。**rise 需要按"一个人格的记忆"来做的操作**有：摘要、备份恢复、待处理事件、放弃事件。如果一个世界里放多个人格，这几项就要能按主体做，不能只按整个世界做。

### 5.3 从种子分叉出副本（必须）

- 给一个来源（种子世界或快照）和新世界名，造一个新世界。新世界的摘要等于来源的摘要。
- 来源是只读的，分叉不改它的任何字节，也不跑迁移。
- 新世界会进注册表，看板能看到。最好能看出它是从哪个来源分叉出来的，以及 rise 给的标签（`run_id`、`session_id` 或 `episode_id`、`slot_id`、`persona_id`）。
- 分叉要快：每个会话开始时都要分叉若干次。按 4.4 的规模，库在 1 MB 上下，整文件复制就够快。
- **不导入旧库**（rise 一侧的决定）。现有的 `.db` 文件只是验证时留下的数据，新系统从空开始，所以不需要"把一个外部文件导入成世界"的接口。种子由 rise 对部署世界拍快照或分叉得到，也可以建空世界作为种子。
- **种子落后于当前 schema 时拒绝分叉**（rise 一侧的默认），返回 `world_schema_behind` 这类可以区分的错误码，不要静默迁移。迁移会改动被锚定的字节。升级种子由人显式来做，升级后得到的是一个新种子。

### 5.4 快照与恢复（必须）

- 给某个世界（或某个主体）拍快照，返回快照的摘要。
- 从快照恢复，返回恢复后的摘要，等于拍快照时的摘要。
- 还有打开着的连接或在途调用时，恢复要拒绝，并返回能区分的错误码（rise 今天按 `restore_from: persona has an open port` 处理，见 `src/actio/memory_starling.py` 的 `restore_from`）。
- 崩溃安全：恢复过程中进程被杀，世界要么还是原样，要么已经完整恢复，不能留下半新半旧的状态。rise 现在为此自己处理了 `-wal`、`-shm` 和 `VACUUM INTO` 的顺序，以后应该由 Starling 负责。
- Starling 已有的世界快照和回滚（PR #111，语义 A）如果满足这几条，可以直接用。
- **rise 拍的快照归调用方所有，不参与"保留 5 份"的修剪。** 部署轮次里每个 episode、每个绑定的人格各拍一份，数量事先不确定，由 rise 在轮次收尾时显式删除。修剪如果删掉了 rise 还要用的回滚点，回滚就会静默失效。
- **恢复前的那份状态**（Starling 的 `pre-rollback` 归档）保留下来供复盘，和训练副本按同一套保留规则处理（rise 一侧的默认，见第 8 节）。

### 5.5 Python 客户端（必须）

- 一个连服务的 Python 客户端。打开某个世界（和主体）后得到一个对象，提供 4.1 表里除 `backup_to(path)` 以外的全部门面方法，**签名和返回值的形状都与 `starling.Memory` 一致**。这样 rise 的适配器 `StarlingMemory` 只需把 `Memory.open(...)` 换成客户端的打开调用。`backup_to` 由 5.4 的快照代替。
- **客户端的接口一律不收文件路径。** 世界按名字找，快照按 id 找，服务只在自己的数据目录里读写。
- 异常照旧：`RecallDegradedError`、`EventConflict`、`MemoryClosed` 在客户端这边按同名类型抛出。连不上、超时、服务端错误要有能区分的类型，并标明是不是瞬态（rise 按瞬态与永久分 T1 和 T2）。
- 异常文字里不要带端点地址或密钥。
- 分叉、快照、恢复、关闭世界、列出世界这些管理操作，客户端也要有。
- `close(timeout=...)` 的语义保留：超时就抛错，并且不把连接标成已关。rise 靠这一点决定保不保留副本。
- 客户端最好只依赖标准库加一个 HTTP 库，**不依赖 C++ 扩展**。这样 rise 一侧以后搬去 GPU 主机时不用编译 Starling。

### 5.6 抽取与嵌入的配置（必须）

- 打开世界时，rise 要能指定抽取和嵌入端点（`base_url`、`model`、`dim`、`timeout_ms`、`max_retries`）。不同世界可以用不同配置，但 rise 一般全用同一份。
- 密钥：服务进程从自己的环境变量读（今天是 `OPENAI_API_KEY`），不走 HTTP 传递，也不落盘。
- 服务要能报出实际生效的抽取配置（`ExtractionConfig` 的值）和版本，rise 要把它们写进记忆运行时身份。

### 5.7 实时可看，结束后保留（必须）

- 会话还在跑时，看板能看到这个世界的语句实时增加。这要求一个世界正被 rise 写着的同时，看板也能读它。
- **看板里任意一个世界都能点进去看**，用户 2026-11-02 定的。点进去能看语句、做召回、用现有的各种检视页面，正在被 rise 写着的世界也一样能看。只看世界列表和语句计数不够。Starling 现有的检视路由和命令路由都只认唯一那个活动世界（`app.state.config`），这些要改成按世界寻址。
- **"实时"的口径**：看板打开着的时候，一个正在写的世界里新增的语句几秒之内就能看到，轮询还是推送由 Starling 定。
- 会话结束后 rise 不再删副本，只把它关掉。复盘时能在看板里找到它，并能按 `run_id`、`episode_id` 过滤。
- **自动清理**，用户 2026-11-02 定的。保留下来的训练副本（以及 5.4 里恢复前的那份状态）按数量或天数自动清理，由 Starling 执行，rise 不再负责删除。
  - 默认值由 rise 一侧先定，Starling 可以改：每个 `run_id` 只留最近 200 份，并且只留 14 天，两条哪条先到按哪条删。这两个数在服务配置里可以调。
  - 部署世界、种子和 rise 拍的快照不参与清理。
  - 正被打开着的世界不删。
- 有了这条上限，注册表里的世界数大约是"每个 run 200 份 × 同时保留的 run 数"。按 Starling 现在的 `worlds.json`（整个文件重写，并持有全局锁）加上逐个打开库取统计的做法撑不撑得住，由 Starling 评估；撑不住就要换存储方式，或者加分页和统计缓存。

### 5.8 后台任务不能改动被锚定的库（必须）

- 看板默认会跑后台 tick（嵌入、巩固、投影、出箱），还有摄入 worker。rise 用的世界里这些都要能关掉，至少是那些会改变 `digest()` 的。否则同一组 rollout 的起点会悄悄漂移，种子的摘要也会变。
- rise 自己决定什么时候 `embed_pending`，用的是事件时钟（4.1）。

### 5.9 启动、就绪与停止（必须）

- 能用一条命令起服务，参数里给数据目录、监听地址和端口、鉴权 token。不读 `~/.starling` 的默认配置，避免和用户自己的看板混在一起。
- 有就绪探针（看板已有 `/health`），起好之前不接受请求。
- 收到 SIGTERM 能安全停：等在途请求结束、关库、不丢已提交的写入。
- 同一个数据目录只能被一个服务进程打开，第二个要报明确的错并退出（`world_in_use` 一类）。
- 用 token 鉴权（看板已有 Bearer token）。只听回环地址时，token 也要能配。

### 5.10 版本可钉（必须）

- rise 按 git 提交钉 Starling（今天是 `pyproject.toml` 里 `starling-memory @ git+...@730e415`）。服务和客户端要能用同一个提交装上。
- 服务要能报出自己的提交或版本，rise 启动时核对它和钉住的一致，并写进训练记录。
- 客户端和服务的协议版本不兼容时，连上就报错，不要等到调用时才出错。

### 5.11 最好有

- 世界的标签和元数据：rise 打开或分叉时能附上一组键值（`run_id` 等），看板可以按它过滤。
- 世界的只读打开：复盘时保证不会被误写。
- 列出世界时带上摘要和最后写入时间，rise 启动时可以据此对账。

## 6. rise 一侧会做的事（供 Starling 一侧参考，不需要 Starling 实现）

- 拉起服务：配置里没给地址，就以子进程方式启动钉住版本的服务，等就绪探针通过；rise 退出时发 SIGTERM。
- 适配器 `StarlingMemory` 和 `StarlingDeploymentStore` 改成走客户端。`TrainingCopies` 改成"分叉一个世界并打标签"，终态只关闭、不删除。
- 部署起点副本和验证快照改用 5.4 的快照与恢复。
- 记忆运行时身份里加上服务报出的版本与提交，替换掉今天的 `starling.__version__` 加安装来源。

## 7. 验收

在 Starling 一侧完成后，满足下面这些，rise 就能接上：

1. 一个服务进程里同时开三个世界，各自 `remember_event` 和 `recall`，彼此看不到对方的语句。
2. 从一个种子分叉出两个副本，三者摘要相同；往一个副本里写，另两个的摘要不变；种子的文件字节不变。
3. 快照、写入、恢复之后，摘要等于快照时的摘要；还有连接开着时恢复被拒，并返回可区分的错误码。
4. rise 在写一个副本的同时，看板里能点进这个副本，看到新语句在几秒内出现，也能在里面做召回；不需要切换"活动世界"，也不影响别的世界的写入。副本关掉之后，看板里还能按标签找到并点进去。
4a. 超过保留上限（数量或天数）的副本会被自动删除；部署世界、种子、rise 拍的快照、正被打开着的世界都不会被删。
5. 关掉后台 tick 的世界，静置一段时间后摘要不变。
6. 用客户端跑一遍门面的这些用法，行为要和进程内的 `Memory` 一致：同 key 同文本重入、同 key 异文本冲突、abandon 之后再写冲突、嵌入失败时 `strict` 召回抛 `RecallDegradedError`、`close` 超时不被标成已关。
   rise 造故障的办法是起一个本机回环的 OpenAI 兼容假端点，放在子进程里（`tests/starling_fakes.py`）。它按事件 key 让抽取回 500 或回坏 JSON，嵌入则按词面给出确定的向量。服务端只要能把抽取、嵌入的 `base_url` 指到这个端点（5.6）就够了，**不需要内置桩模式**。Starling 自己的确定性测试要不要加桩模式，由 Starling 决定。
7. SIGTERM 之后再起服务，已提交的写入都在；同一个数据目录起第二个服务时，第二个报错退出。
8. 服务报出的提交等于安装时钉住的提交。

## 8. 待定

## 9. rise 一侧替 Starling 先定的默认

下面几项由 rise 先定了默认值，Starling 一侧可以改，改了告诉 rise 就行：

- **句柄模型**（5.1）：每个客户端会话一份句柄；另一个会话来写同一个世界，就拒绝；客户端断开就释放。
- **旧库不导入，新系统从空库开始**（5.3）。
- **种子落后于当前 schema 时拒绝分叉，不静默迁移**（5.3）。
- **rise 拍的快照不参与修剪**；恢复前的状态保留下来，供复盘（5.4）。
- **保留上限默认每个 run 200 份、14 天**（5.7），可以在配置里调。
